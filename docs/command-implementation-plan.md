# BudgetManagementBotSystem — コマンド実装計画

このドキュメントは Discord スラッシュコマンドの実装順序・依存関係・優先度を整理します。

実装済みコマンドの最新状況は [実装状況](implementation.md) に集約し、この文書では未実装コマンドの優先度と依存関係に絞って整理します。

## 目的

この文書は、現時点で未実装または実装途中の Discord スラッシュコマンドについて、実装順序・依存関係・担当レイヤーを整理した計画書です。実装済みのコマンドは [実装状況](implementation.md) に集約しています。

## 現状認識

- `Presentation/Discord/Modules` に主要なコマンド定義が存在している
- 多くのコマンドは UseCase / Query UseCase まで接続済み
- 既存の実装済みユースケースは申請作成・承認・却下・取消・予算増額・班登録・ユーザー登録/更新に集中している
- 申請ワークフロー、予算参照系、管理系の主要コマンドは概ね実装済み
- 現行の `ApprovalModule` では `/approve` スラッシュコマンドが公開されていないため、Discord UI から承認操作を行う場合は再追加が必要

## 推奨実装順序

1. `/approve` スラッシュコマンドを再公開するか、承認操作を別の UI に寄せるかを決める
2. 申請ワークフローの通知文言と embed 表示を統一する
3. 管理系コマンドの権限表と運用ポリシーを固定する
4. クエリ系コマンドのページング・空結果・権限制御のテストを増やす
5. 運用系（班削除の運用ポリシー策定など）を完了する

## コマンドごとの実装メモ

- 申請系は「作成」「一覧」「詳細」「状態変更」を分離する
- 承認系は状態遷移ルールと監査情報の永続化を優先する
- 予算系は年度の扱いを統一し、集計 Query を再利用する
- 管理系は CRUD だけでなく、無効化や所属解除の扱いを明確にする
- 集計系は専用 Query を用意し、Presentation 層に集計ロジックを置かない

## テスト計画

- Application 層のユースケース単体テストを先に追加する
- 状態遷移を伴うコマンドは正常系と異常系の両方を必須にする
- 一覧系はページング・フィルタ・空結果を確認する
- 権限制御があるコマンドは、権限あり・なしの両パターンを確認する

## 補足

この計画は、既存の実装済みユースケースを活かしながら、依存が小さいものから順番に積み上げる前提で書いています。実装が進んだら、この文書の各コマンド行を「未実装 / 実装途中 / 実装済み」に更新してください。

注: 管理系コマンド（例: `/register-user`, `/set-user-role`, `/assign-group` など）は、以前は文字列で Discord ユーザー ID を受け取っていましたが、実装を `IUser` 相当の `user` パラメータへ変更しました。これによりスラッシュコマンドの UI 上でユーザーを選択でき、`targetUser.Id` から内部で Discord ID を取得します。手入力の ID ではなくユーザー選択が推奨されます。

## UI改善の反映状況

- 第一段階のUI改善として、主要コマンドの応答をEmbed表示へ統一しました。
- `DiscordEmbedFactory` に成功、情報、警告、権限不足、入力不備、対象なし、予期しないエラー用の共通Embed生成を追加しました。
- 予算、申請、承認、ユーザー、班、システム系の主要コマンドは、プレーンテキストではなくEmbedで結果を返します。
- `/menu` コマンドを追加し、ログインユーザーのRoleに応じた主要コマンド一覧を表示します。
- Autocomplete、ボタン、Modal、ページングボタンは今回の第一段階では対象外です。
