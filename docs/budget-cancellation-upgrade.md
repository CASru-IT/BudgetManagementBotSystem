# 予算取消機能の更新手順

## 適用前

- 稼働中のソース・設定とGitHub developとの差分を確認する。ローカルや本番だけに存在する修正を、このブランチで上書きしない。
- Botを停止し、PostgreSQLのバックアップ（`pg_dump`）を取得する。復元先と旧イメージを記録する。
- 旧バージョンと新バージョンを同時に稼働させない。旧バージョンは班の更新トークンを更新しないため、競合検出が成立しない。
- 本番適用前にDBの複製で起動・取消・残高・履歴表示を検証する。

## 起動時のDB更新

既存の `EnsureCreatedAsync` に続き `BudgetCancellationSchemaUpgrade.ApplyAsync` を実行します。PostgreSQLのみ対象で、単一トランザクション内で以下を追加します。既存の行や金額は変更しません。

- `Groups.BudgetRevision`（uuid、既存行はゼロ値）。EF Coreの同時更新トークン。
- `BudgetTransactions.Kind`（整数、既存行は0=Legacy）。1=BudgetAddition、2=ApprovalRefund、3=BudgetCancellation。
- `ReversesTransactionId`、`CancelledByUserId`、`CancellationReason`（最大500文字）。通常取引ではNULL。
- 取消元取引IDの一意インデックス、取消元取引と実行者への外部キー。

処理は再実行可能です。DDL権限がない場合や制約作成に失敗した場合は起動を中止します。新規DBはEFモデルから同じ構造と既定値を作成し、更新処理でも既定値を補います。起動時のGuild/Global登録設定に従って `/予算履歴` と `/予算取消` が追加されます。

## 動作確認

テスト用の班に追加予算を作成し、履歴IDを指定して取消を確認します。キャンセルでは残高が変わらず、確定すると元の年度だけ減額され、同じIDの再取消が拒否されることを確認してください。

## 切り戻し

- 新Botを停止してから旧バージョンへ戻す。追加列は残したままにする。
- 取消記録は既存モデルでも通常の支出として計算されるため、残高計算には反映される。ただし取消理由・対応関係・競合検知は旧UIでは利用できない。
- 更新後の操作があるDBに更新前バックアップを上書きすると、その間の申請・取引を失う。復元は更新後の操作を保全・照合してから行う。

## 検証

`dotnet test` はSQLiteの独立したDBで取消記録の保存、外部キー、同時更新失敗時のロールバックを検証します。PostgreSQL固有の起動DDLは、テスト専用インスタンスの接続文字列を `BUDGET_TEST_POSTGRES` に設定して実行します。この接続ユーザーにはCREATE DATABASE権限が必要です。テストはランダム名のDBを作成し、終了時にそのDBだけを削除します。本番DBの接続文字列は使用しないでください。

PostgreSQL統合テストは既存スキーマと新規スキーマの双方で、更新の再実行、旧バージョン形式のINSERT、残高・元履歴の保持、一意制約、同時更新時のロールバックを検証します。接続設定がなければこの統合テストはスキップします。
